LLM Council · Tandem · Wave 1.4

BUG-72 — should the four Group C objects be dropped?

2026-08-14 · convened under the standing directive to route judgment calls to the council

The finding that changed the question

The object being audited as “unused clutter,” progressive_overload_recommendations, turned out to have this body:

WHEN min_reps_hit >= 10 THEN round(weight_lbs * 1.025 / 5.0) * 5   -- +2.5%
WHEN min_reps_hit >= 7  THEN weight_lbs                            -- hold
ELSE GREATEST(round(weight_lbs * 0.95 / 5.0) * 5, 5)              -- -5%

That is a fixed ±2.5% ratchet — the exact thing D11 forbids (“the working 1RM must be earned, never a fixed weekly step”). It is PostgREST-addressable and has no consumer today.

This reframes BUG-38, which was filed as “the ±2.5% ratchet still exists” and then marked likely stale because the JS function it named never existed. The ratchet was never missing — it lived in the database as a view, where doctrine.mjs (a Node script that reads repo files only, with no DB connection) structurally cannot see it.

Council verdict

Drop all four. Unanimous, 5/5.

Not one advisor argued to keep any object. The clash was never about the drop — it was about scope: whether the drop may ship without a DB-connected gate to replace the blind spot it exposes.

Where the council clashed

Contrarian, First Principles, Expansionist (+ 2 of 3 reviewers): the drop must not merge alone. Delete the view and npm run verify is still green for the same wrong reason. The real deliverable is a DB-connected gate — an object allowlist, a doctrine-db.mjs, a new invariant D17.

Executor (+ the pragmatic reviewer): that is a wave, not a cleanup ticket. And the proposed remedy has a defect its own proponents missed — a checked-in schema snapshot rots silently and passes green, which is the same failure class it claims to fix.

Blind spots caught in peer review

Four emerged only in review. Three were verifiable rather than arguable, so they were verified.

1. The anon GRANTs were never checked. Verified — and it was worse than assumed. All four objects carry anon=arwdDxtm: full privileges, not read-only. exercise_notes has RLS + 1 policy backstopping it, so this is not a live hole — but the brief’s reasoning (“security_invoker means own-rows-only”) was not the thing actually protecting it.
2. Sweep for siblings before deleting the search key. Done. Swept every view body and every pg_proc.prosrc in public for 1.025 / 0.95 / 1.05 / 'increase weight' / 'reduce weight'. Exactly one hit: the view itself. The blind spot has exactly one sample.
3. Nobody verified disuse at runtime. Done. 0 PostgREST hits across all four objects in the available log window, on top of 0 code references and 0 pg_depend dependents.
4. D17 cannot land in this commit. Two reviewers caught this independently: CLAUDE.md mandates Notion → DOCTRINE.md → doctrine.mjs, in that order. Inventing an invariant inline to satisfy a cleanup ticket would violate the very doctrine-is-law rule being invoked to justify it. This is what breaks the tie.

The recommendation

Drop all four now. File the blind spot; do not build it into this commit.

The scope argument is correct about the diagnosis and wrong about the vehicle. Holding a four-object cleanup hostage to an unbuilt gate would leave a known D11 violation live in production while the “proper” fix is designed. That trade is backwards.

The Contrarian’s fear — “you’ll have burned the one piece of evidence” — is answered by the migration itself: the verbatim CREATE VIEW body is preserved in the rollback block, in git, permanently. The evidence survives; only the executable artifact dies.

Reject the Expansionist’s rebuild-as-read-model and keep-the-idea proposals outright — three hypothetical features attached to a deletion, in a repo whose standing rule is “don’t design for hypothetical future requirements.”

Advisor responses in full

The Contrarian — “shipping only the DROP is a trap”

Drop all four. That’s the easy part, and it’s also a trap — shipping only the DROP lets everyone declare victory over a problem you haven’t touched. The ratchet view is not the bug. The bug is that a doctrine-violating recommendation engine lived in production for months and your LAW-grade gate returned green the entire time, because the gate reads files and the violation lived in Postgres.

Two things you’re taking on faith: “Zero references” is a grep of THIS repo — it doesn’t cover saved queries, edge functions, or untracked bundles in your working tree. And “reversible via rollback block” is false in your environment: execute_sql DDL never lands in schema_migrations, so a rollback block in a file nobody applied is a comment, not a safety net. Also, security_invoker = on is not the same as “not exposed” — check the actual GRANTs to anon.

The First Principles Thinker — “two engines, one governed”

You’re asking “drop or keep four objects?” The actual problem is that you have two engines and only one is governed. Doctrine is enforced against files because doctrine was written against files — an accident of tooling, not a principle. The principle is “every surface that can tell a human what weight to lift is bound by D11/D12.” Postgres is such a surface and has never once been gated. This view isn’t a bug you found; it’s the first sample from a blind spot of unknown size.

The ratchet view: drop — not because it’s unused, but because “unused” is the weakest possible defense of a thing that violates law. It’s one .from() call from being real. The other three compute nothing prescriptive; cost of existence zero, cost of deletion zero — that symmetry means the question is genuinely uninteresting, and spending council cycles on it is how you avoid the interesting one.

The Expansionist — “the blind hemisphere is the real find”

Drop all four — but BUG-72’s real deliverable is the blind hemisphere you just found. Everything in Postgres — view bodies, PL/pgSQL, triggers, RLS predicates — is invisible to the gate. An entire class of violations that can never be caught, and you found one on the first look. Build scripts/doctrine-db.mjs: introspect pg_get_viewdef / pg_proc.prosrc / pg_policy, write a checked-in snapshot, let the existing file-reading gate audit it.

Second: that view body isn’t trash, it’s a fixture — check it into the doctrine tests as the canonical negative example. Third: the view’s shape is a free spec for a server-side read model that would unlock cron nudges and notifications. (Chairman’s note: rejected as scope creep.)

The Outsider — “you’re counciling an action with an undo button”

Drop all four. When undo is one migration away, “keep it just in case” isn’t caution, it’s a decision you’re declining to make.

Two pieces of reasoning I don’t buy. “Deletes a future feature’s landing zone” — an empty view is not a landing zone; nothing lands on it. What you’d preserve is not capability, it’s the feeling of having already started. “Evidence needed to close BUG-38” — evidence is a paragraph and a definition, not a live production object. Keeping a running artifact as its own exhibit is how a two-person app accumulates a museum.

The thing nobody is saying: the ratchet didn’t survive because someone was careless. It survived because your gate reads files and your team reads gate output, and “the gate is green” quietly became “the system is compliant.” That substitution is the actual bug.

The Executor — “one migration, this afternoon”
  1. Copy the four CREATE bodies into the rollback block — that’s your BUG-38 evidence. Evidence lives in the migration file and the ticket, not in prod.
  2. DROP VIEW progressive_overload_recommendations — not a judgment call.
  3. Drop medal_comparison and weight_trend in the same migration. “Cheap to keep” is wrong framing — the cost is that every future audit re-litigates them.
  4. Drop exercise_notes, and in the same commit delete the DELETE line from test-users-purge.sql, or the purge script errors on a missing table next month.
  5. Run via execute_sql and record it in the ticket, since the ledger under-reports.
  6. Close BUG-38 citing this commit; its premise was wrong and the real artifact is now gone.
Peer review highlights (3 reviewers, anonymised inputs)

Reviewer 1 — Strongest: the Contrarian, the only one treating the brief’s own claims as falsifiable. Biggest blind spot: the Executor’s pure-hygiene framing. All five missed: runtime evidence of disuse; that a checked-in snapshot silently drifts; and that CLAUDE.md requires Notion-first before D17.

Reviewer 2 (skeptical) — Strongest: the Contrarian. Biggest blind spot: the Executor — recommends running DDL via execute_sql and tracking it in a ticket, normalising the exact ungoverned path that let the ratchet hide. All five missed: sweep pg_proc and triggers for sibling ±2.5% logic while the signature is still in hand — you’re deleting the search key.

Reviewer 3 (pragmatic) — Strongest: the Executor, the only shippable sequence, and the only one catching that dropping exercise_notes orphans the purge script. Biggest blind spot: the Expansionist — three hypothetical features attached to a four-object deletion, in a project with an explicit anti-over-engineering rule.

Carried forward — not closed by this council

  • The gate’s DB blind spot — file to Notion as a proposed invariant (D17: no database object may emit prescriptive load). Notion first. Do not write it into DOCTRINE.md or doctrine.mjs inline.
  • Any future schema-snapshot approach: a stale snapshot passing green is the same failure class. Freshness must itself be gated, or don’t build it.
  • Residual risk, stated plainly: the two Edge Functions (qa-session-validator, expand-and-log-bug) were not read. Both are QA/bug-logging tooling, and 0 runtime hits corroborate that neither consumes a progression view. If one did, the rollback block restores the object in one statement.
