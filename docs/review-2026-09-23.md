## Confirmed findings

### C1 · P0 · Streak and total-session counts are double-counted on every finish — live drift on all 4 accounts
**Not previously logged** (no Notion entry covers streaks/points double-crediting; nearest is
BUG-125, a different anomaly, Resolved).

- **Where:** two homes for one rule. DB trigger `update_streak_on_complete` → `update_streak()`
  (fires on `workout_sessions.completed` false→true) AND JS `creditSessionToStreaks()`
  (tandem.html:6349–6391), called from `finishSession()` at :6587 *after* the `completed=true`
  UPDATE at :6568 has already fired the trigger. Both increment `total_sessions` (and the trigger
  path + JS path each maintain `current_streak_days` by different rules).
- **Repro (read-only SQL, run 2026-09-23):**
  ```sql
  select u.email, s.total_sessions, s.total_prs,
         (select count(*) from workout_sessions w where w.user_id=u.id and w.completed) as actual_sessions,
         (select count(*) from personal_records p where p.user_id=u.id) as actual_prs
  from streaks s join users u on u.id=s.user_id;
  ```
  Output: kerwinferrette@gmail.com `total_sessions=33` vs `actual=18`, `total_prs=57` vs `51`;
  dgaumer03 `3` vs `2`; both test accounts `total_prs=0` vs actual `10` and `6` (PRs written by the
  DB trigger path never credited by the JS path — the two homes also *disagree in both directions*).
- **What should happen:** one owner for the streak/session-count rule ("one rule, one home");
  whichever side keeps it, the other must stop writing.
- **Mechanism, not instance:** every finisher goes through this pair — program-day finish, one-off
  finish, journal backfill. `current_streak_days` also advances once per *session*, not per *day*
  (two same-day sessions = +2 "days"), and the DB trigger's same-day branch is a silent no-op while
  the JS branch is not — so the drift is unbounded and direction-inconsistent.

### C3 · P1 · Log tab renders permanently empty after device change or cloud restore
**Not previously logged.**

- **Where:** `buildLiftSeries()` (tandem.html:6724–6748) reads ONLY localStorage `tandem_history`
  (capped at 100 sessions by `finishSession()`'s `hist.pop()`), filtering on `sess.date` and
  `sess.exercises`. `restoreFromCloud()` (:7058+) maps cloud `workout_sessions` rows straight in —
  those rows have `session_date` (not `date`) and no `exercises` map, so every restored row fails
  both checks (`new Date(undefined)` → NaN → filtered).
- **Repro:** node shape-check over the two code paths' emitted objects (run in session): a
  `restoreFromCloud`-shaped row yields 0 series points; a `finishSession`-shaped row yields normal
  points. On a fresh device with full cloud data, `renderLogTab()` (:6761) therefore draws nothing.
- **What should happen:** Log history's source of truth should be the `sets` table (which is
  complete and durable), or restore must write the exact `tandem_history` shape.
- **Mechanism:** any consumer of `tandem_history` shares this — the shape contract has no owner and
  no gate. The 100-session cap also silently truncates long-term history even without a restore.

### C4 · P1 · Calendar-day arithmetic is DST-unsafe — today's workout index and overdue detection shift by a day
**Extends BUG-27 (Investigating: "Workout day shows Friday instead of Saturday")** — same
mechanism, two concrete sites named.

- **Where:** tandem.html:8104 (`getWeekSchedule()` → `todayIndex`) and :8353 (overdue-gap calc):
  `Math.floor((today - start) / 86400000)` over local-midnight Dates.
- **Repro (run):** `TZ=America/New_York node` with start `2026-03-07`, today `2026-03-09`
  (spring-forward on 03-08): elapsed = 47h → `Math.floor(47/24) = 1` day, calendar answer is 2.
  Output reproduced in session: `dayIndex=1, expected=2`.
- **Effect:** for the week containing a DST change, the highlighted "today" cell, cadence position
  and overdue flag are all off by one (US springs forward every March — Kerwin & Dani are affected
  annually).
- **What should happen / mechanism:** one shared calendar-day-diff helper (e.g. UTC-noon anchored or
  `localDateStr` string math) used by *both* sites; today each site re-derives it.

  out streaks and totals from the actual workout rows, so they can't be counted twice. Kerwin's

- **S1 — CONFIRMED, then FIXED** in `migrations/0019_pairing_consent.sql`. Proven on the test
  accounts, with every test rolled back afterwards. There were two problems:
  - `connect_partner()` paired you with anyone, without their consent.
  - **Worse:** because the partner check was one-sided, a user could set their *own*
    `partner_id` to anyone and read that person's data. One test account went from seeing 0
    of the other's sets to all 22.
  - After the fix, re-running both attacks fails: pairing needs both people to agree, and a
    stranger sees 0 sets.
