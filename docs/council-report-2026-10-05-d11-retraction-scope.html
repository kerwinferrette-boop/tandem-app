LLM Council · Tandem

Does recomputing a stored 1RM downward after a set is deleted violate D11?

2026-10-05 · attended session · 5 advisors, 5 anonymized peer reviews, chairman synthesis
Full transcript: docs/council-transcript-2026-10-05-d11-retraction-scope.md

The question

Kerwin's local history shows Good Morning 905 lbs × 12 (Epley est. 1RM 1267). It is physically impossible and it is not in Supabase — cloud sets tops out at 135 × 10 (est. 180) and personal_records = 180. The 905 lives only in localStorage.tandem_history, because the cloud-hydrate path is add-only and nothing prunes a local entry the cloud lacks. The History modal is read-only, so he cannot correct it.

The requested fix recomputes the stored PR and working 1RM from the sets that remain — which lowers them. D11 is ACTIVE and SAFETY tier (no override ever authorized), and its own text says the running max is one-sided: a session "can only fail to raise a number, never lower one."

Reading A: outside D11 — one-sidedness is a property of the operator; retracting a never-real entry changes the input set. Reading B: a violation — "never lower" is literal and SAFETY tier, so the invariant must be amended first.

At stake: the gate text-greps one function, so a new lowering function elsewhere would pass CI fully green while a live SAFETY-tier violation sat in the product.

Council verdict

Reading A is correct in principle — but it must not be implemented as a lowering path. Ship it as a void (tombstone), and do not weaken D11: split it.

A voided set is filtered out of the input set, so the max operator stays one-sided and nothing "lowers" a measurement. That dissolves the A-vs-B fight instead of betting on it — which matters, because D11 is SAFETY tier and per D16's tierGuard no override key exists, so under Reading B the feature could not ship at all and the council has no standing to settle that bet unilaterally.

Split the invariant: D11a = the prescription curve never dips. D11b = the max operator is one-sided over the set of valid measurements. New clause: validity is a property of the input, not the operator; a voided set is not a measurement. Notion first, then DOCTRINE.md + scripts/doctrine.mjs in the same change. This amends for underspecification, not as an exception.

One home + a real gate: a single deriveBestFrom(sets) that every derivation path calls, asserted behaviorally — and enumerate every writer of tandem_prs / tandem_working1rm, failing on an unregistered one. Text-grepping the inside of one named function is, in the Contrarian's words, "a comment with CI privileges."

Do first, before any code: clear the 905 from Kerwin's browser and verify at the pixel that Good Morning reads 180 — then audit what est-1RM 1267 already prescribed. The ghost is cosmetic; what it already told a human to lift is not.

Full responses

The Contrarian (anonymized as C) — picked strongest by all 5 reviewers

The fatal flaw: you are debating doctrine about a feature that doesn't fix the bug you have.

The 905 exists because the hydrate path is add-only and never prunes local entries the cloud lacks, and because nothing rejected 905 x 12 at entry. A delete button fixes this one ghost. The next one needs another button press. That is textbook fix-the-instance-not-the-mechanism, the exact rule this repo already has in writing. The real fixes are (1) a reconcile that prunes local-only sets, and (2) an entry-time plausibility bound. Neither touches D11.

Reading A collapses under one question: what distinguishes "a set that was never real" from "a set the user wants gone?" Nothing. At runtime there is no truth oracle — there's a button. A's whole argument rests on "corrected input set," but the code cannot verify the correction. So you haven't changed the input set; you've handed the user a downward ratchet on their own measured max. In a competition app between two people whose progression difficulty is driven by that number. The incentive to lower it is structural, not hypothetical. That is squarely inside D11, and SAFETY tier means it does not ship on a clever scope argument.

Second flaw nobody's raised: it won't even work at the pixel. Cloud personal_records stays 180, monotonic, unlowerable. Local drops. Next hydrate the number climbs back and the user watches their deletion undo itself — a toast saying "fixed" over a value that wasn't. That's reorderWeek() again.

If you amend anything, amend the gate first: enumerate every writer to tandem_working1rm/tandem_prs and assert the one-sided guard across all of them. A grep inside one function is not an invariant; it's a comment with CI privileges.

The First Principles Thinker (anonymized as E)

You're asking a doctrine-scope question about a data-integrity bug. Wrong question.

Strip it down. What are you actually trying to solve? The local cache can contain records that never happened, and nothing can remove them. The 905 isn't a bad measurement. It isn't a measurement at all. It's a cache artifact of an add-only hydrate path. D11 is a theory of how measurements compose; this value never entered the measurement domain, so D11 has literally nothing to say about it, and arguing (A) vs (B) is arguing about which law governs a thing that isn't in either jurisdiction.

Notice what the real defect is: the hydrate path is add-only. Local can hold what cloud denies, forever, with no reconciliation. An Edit/Delete button is a manual workaround for a sync engine that has no concept of authoritative source. Build the button if Kerwin wants it — but if that's all you build, the next phantom arrives the same way and he files the same bug again. Fix the mechanism: local history must be reconcilable against cloud, which already holds 135×10.

And reframe the invariant. D11 says "never lower one," which conflates two different things: monotonicity of the max operator (correct, SAFETY) and immutability of stored history (never argued for, never cited, accidentally smuggled in by the word "never"). That conflation is the actual bug in your doctrine. The right rule isn't "numbers never go down" — it's "derived values are never authoritative; they are always recomputable from the set of real measurements." Under that framing, recompute-downward on deletion isn't an exception you have to carve out. It's the invariant working correctly.

Amend for the right reason: D11 was underspecified, not wrong.

The Expansionist (anonymized as A) — flagged as the biggest blind spot by all 5 reviewers

Reading A is right, but you're all asking too small a question. The real find here isn't "can we delete a set" — it's that D11 has been silently missing a whole half of itself. D11 governs the operator. Nothing in the doctrine governs the provenance of the inputs. That's the gap, and it's worth far more than this one ghost set.

Name it now: D35 — Retraction. A measurement can be retracted; retraction recomputes the max over the surviving record. One rule, one home: a single recomputeBestFrom(sets) function that every lowering path must call — no exceptions, no second entrance. Gate it the way check #27 gates D34: not a text-grep (that's the blind spot you already identified), but a behavioral assertion — feed it a set list, assert the recomputed max equals max(remaining) exactly, and assert that no path lowers a max without a retraction event in the audit log.

That audit log is the undervalued asset. Once retraction is a first-class, logged event, you get things you can't get today:

  • The cloud divergence becomes measurable. The 905 ghost proves the hydrate path is add-only and silently lies. Retraction events give you a reconciliation primitive — local-vs-cloud drift detection, which is a whole class of bugs you currently can't see.
  • Dani can dispute Kerwin's PRs. This is a competition app. A couples-facing "flag this lift" flow turns a data-integrity chore into the product's most social feature.
  • Edit/Delete on sets is the entry point to a real set editor — correcting reps, fixing a mis-tapped exercise. The modal becomes write-capable once, and everything downstream benefits.

Don't amend D11. Extend the doctrine with the axis it never had, and ship the mechanism, not the instance.

The Outsider (anonymized as B)

I know nothing about exercise science, and that's useful here, because a stranger reading your own words hits a wall immediately:

D11 is two different rules wearing one name. Read it cold. The headline is about a prescription curve — "the prescribed %1RM curve rises-or-holds every week." That's a statement about what the program tells the user to lift. Then there's a parenthetical mechanism about calcRM being one-sided. Those are not the same claim. A fresh reader cannot tell which one the gate is protecting, because the gate greps a string inside one function and the failure message talks about "a fatigued session," which is a third thing — an input-provenance condition, not an operator property.

So the honest answer to "is this inside D11's scope?" is: nobody can tell, and that's the actual defect. You're arguing about the intent of a sentence that bundles a goal, a mechanism, and a threat model together. Reading A and reading B are both legitimate because the text supports both. That's not a tie to break; that's a specification bug.

What an outsider would do: split D11 into the two rules it already contains. One about prescriptions never dipping. One about the measurement operator. Then the delete case answers itself — it's clearly not the first, and whether it's the second depends on a question you haven't written down anywhere: is a logged set authoritative, or is it a claim that can be retracted? That's the real invariant you're missing, and it's absent from the doctrine entirely.

Also, plainly: the gate checks that a string exists. That isn't enforcement, it's a spelling test. Any rule worth SAFETY tier should be checked by behavior.

The Executor (anonymized as D)

Reading A is correct but it doesn't matter yet, because you've conflated two shippable units and one of them is a five-minute job.

Monday morning, 9am: unblock Kerwin without touching D11 at all. The 905 lb set is a corrupt cache entry in one browser. Open devtools on his machine, delete the entry from tandem_history, and delete the tandem_prs/tandem_working1rm keys for Good Morning so the next hydrate re-derives them from Supabase (135x10 → 180). Done. No PR, no gate, no council artifact in the critical path. Do that first and stop treating the feature as the fix for the symptom.

9:15am: the real bug is the hydrate path, not the missing Edit button. Add-only hydrate that never prunes local entries the cloud lacks is the mechanism; the ghost set is the instance. A reconcile-on-hydrate that drops local sets with no cloud counterpart fixes every ghost, for both users, forever — and it never lowers a 1RM from a measurement, it lowers it by removing a non-record. That ships under reading A with far less doctrine surface than a user-facing delete button, because the trigger is "cloud is authoritative," not "user said so."

Then, and only then, the Edit/Delete feature. It needs the amendment, so don't start it before the Notion/DOCTRINE/doctrine.mjs change is merged.

The gate work is the one thing you cannot defer or hand-wave: text-grepping the inside of one named function is not a gate, it's a comment. Whatever you write next must assert over all writers of tandem_working1rm/tandem_prs — enumerate the write sites and fail on an unregistered one. Otherwise you've built the silo this question is about.
