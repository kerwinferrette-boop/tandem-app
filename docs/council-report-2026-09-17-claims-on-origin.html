The question Should Tandem ship scripts/claims-on-origin.mjs (+ npm run claims:check) — a gate that checks whether a commit sha is an ancestor of origin/main — plus SC-18 and a loop-config.md rule requiring every Notion "In Fix/Resolved" status write to pass this check first? Context: BUG-49 and BUG-57's Notion pages both described completed, gate-green fixes that turned out to not exist on any remote ref. Small, mechanical, non-design change; gates already green; no app code touched.

Where the Council Agrees

Ship it. All five advisors converge even after cataloguing real gaps — cheap, mechanical, zero app-code touched, closes a hole that has bitten Tandem twice.

Unanimous weak point: merge-base --is-ancestor is necessary but not sufficient. It proves a sha exists on origin/main — not that the sha implements the claimed fix, survives a rebase, or is actually deployed. And a check that's invocable but not invoked at the moment of the status transition is the same "wired but not working" pattern this repo already warns about (EPIC-8a's rest_seconds).

Where the Council Clashes

Scope, not shippability. The Expansionist wants this generalized immediately into "claims must be provable against reality" infrastructure everywhere (CI wiring, audits, program-snapshot, doctrine promotions). Every other advisor and all 5 peer reviewers push back — generalizing before the narrow fix is even proven is premature.

Secondary: the First Principles Thinker argues the ordering is backwards — resolution should require a sha as evidence first, with claims:check as confirmation, not a pre-flight habit. Not resolved by the group.

Blind Spots the Council Caught

All 5 peer reviewers independently caught what all 5 advisors missed: nobody proposed actually running the script against a real uncommitted/unpushed sha to confirm it fails loudly. "We wrote a check" ≠ "we verified the check catches the thing."

Related: no advisor made "does failure actually block the Notion write, or is it just a documented habit" a hard shipping blocker — which is the entire point of the change.

The Recommendation

Ship, scoped to exactly BUG-49/57's failure mode — not the Expansionist's broader vision. Two concrete pre-merge requirements: (1) prove the script fails loudly on a real never-pushed sha, in the commit body; (2) state the enforcement mechanism honestly in loop-config.md (enforced vs. procedural). No CI wiring / audit gating / doctrine-promotion gating bundled into this change.

The One Thing to Do First: run claims-on-origin.mjs against a real sha and confirm it rejects with a clear failure — write that result into SC-18 and the commit as verification evidence.

Full Advisor Responses

The Contrarian

This gate checks the wrong thing at the wrong time. git merge-base --is-ancestor only proves a commit exists on the remote — it says nothing about whether it implements the claimed fix. BUG-49/57 failed because someone wrote "done" without citing a sha at all. Real gap: does the Notion write path even require a sha field before status flips? If optional, this ships as decoration.

Second hole: timing — a sha can stop being an ancestor after a force-push/rebase and nothing re-verifies it. Third: who runs this, and can it be skipped? A script that's invocable but not wired into the actual write is exactly the "green gate asserting a dead value" pattern CLAUDE.md warns about. Before shipping: confirm the sha field is mandatory and wired into the actual write.

The First Principles Thinker

The question that matters isn't "does the script check ancestry correctly" but "why did anyone believe a commit existed before checking?" BUG-49/57 were a social/procedural failure — a status field used to record intent-that-feels-done, not verified-done. git log was always available; nobody ran it.

Ship it anyway — cheap, mechanical, converts a manual lapse into an automatic one. But the real fix is upstream: resolution should require a sha as evidence; the script should confirm, not gate. One gap: doesn't catch a reverted commit or an undeployed one (Netlify build failure) — ancestor-of- origin/main is necessary, not sufficient.

The Expansionist

Ship it — but this is bigger than BUG-49/57. It's the first piece of "claims must be provable against reality" infrastructure Tandem needs everywhere: the doctrine gate can't see the database, the preview-server false negative, SC-03's "run don't simulate" — all the same disease.

Extend the ancestor-check idea to the should/could/did audit itself and to program-snapshot.mjs's baseline hash. Make claims:check a required CI step, not just a local script. Gate every status transition that asserts existence-on-remote, including Epic "Done" and doctrine PENDING→ACTIVE promotions.

The Outsider

I don't know what BUG-49/57 are and don't need to. Someone claimed work was "done" and it wasn't saved anywhere durable. The fix is boringly standard version-control hygiene. Ship it.

But: "gates are green" is invoked as reassurance for a fix to "gate-greenness lied to us twice" — that's circular. Did anyone actually reproduce the BUG-49/57 scenario against this new script and watch it fail loudly? "We wrote a check" ≠ "we verified the check catches the thing" — this project's own "verify by running, not reading" rule should apply here too.

The Executor

Ship it. Monday-morning-shippable in an hour. The build: git merge-base --is-ancestor wrapped in a script, an npm alias, two doc edits — no logic beyond that.

Real gaps, not theory: where does the sha come from at the call site (manual vs. automated Notion write)? origin/main needs a fresh git fetch or stale local refs give a false pass. Both fixable in the same PR. Ship today.

Peer Review Highlights

Convergent findings (5/5 reviewers)

Strongest response: The Executor — turned criticism into a concrete, testable checklist while still committing to ship.

Biggest blind spot: The Expansionist — proposed scope expansion before confirming the narrow fix works; "premature generalization dressed as ambition," a reversal of the project's own "fix the mechanism, not the instance" principle.

What everyone missed: nobody proposed testing the script against a real never-committed sha to confirm it fails loudly, and nobody made "does failure actually block the Notion write" a hard shipping blocker.

Post-Council Execution (same session)

Both recommendation items completed before commit:

1. Live 3-case test: real merged sha (pass) / real local-only unpushed commit (fails "not an ancestor") / fake sha (fails "not a known commit") — all correct.

2. loop-config.md rule 6 amended to state plainly that the check is procedural , not automatically enforced — no single controlled Notion-write code path exists to call it for you.

Shipped scoped to exactly the council's recommendation — no CI wiring, audit gating, or doctrine-promotion gating bundled in.
