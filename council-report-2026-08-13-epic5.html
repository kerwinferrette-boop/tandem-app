LLM Council — should EPIC-5 (anon key rotation) still be built?

2026-08-13 · Tandem · 5 advisors, convened during Wave 1.2 · verdict: unanimous

The question put to the council

EPIC-5 is a P0 Critical epic, written by Kerwin, titled "anon key rotation — security hardening before public URL share." It hard-gates EPIC-30. But tandem.html:1850 ships an sb_publishable_… key, which Supabase's own docs rate risk "Low" and describe as "safe to expose online: web page, mobile or desktop app, GitHub actions, CLIs, source code." The premise appears obsolete. Overriding it is a call against the author's written intent — so: build it, close it, or replace it?

Where the council agrees

Rotation is not the fix. The gate is.

All five advisors independently reached the same shape: close the rotation scope as premised on an obsolete key model, but do not delete EPIC-30's dependency gate — replace it with the hardening that actually applies. Deleting the gate outright was rejected by every advisor, including the two most eager to close the epic.

Rotation buys nothing for confidentiality (the new key is republished in the same file on the next deploy), nothing for rate limiting (Supabase quotas are per-project, not per-key), and it actively destroys the audit trail you would want if someone had scraped the data.

Blind spots the council caught

Three things surfaced that the original framing missed entirely.

1 · The write side was never audited — and the BUG-74 verification proved nothing about it. The *_write_own policies are declared FOR ALL, covering INSERT/UPDATE/DELETE, and were authored by the same hand, same day, same file as the *_read_all policies BUG-74 had to tear out. BUG-74's post-fix check returned [] on reads. That says nothing about whether anon can still DELETE FROM sets.

Acted on immediately. Result:

as anon, no JWT — rolled-back transactions against prod

  UPDATE public.sets              ->  0 rows   denied   ✓
  UPDATE public.users             ->  0 rows   denied   ✓
  DELETE public.streaks           ->  0 rows   denied   ✓
  DELETE public.medals            ->  0 rows   denied   ✓

  UPDATE public.user_bug_reports  -> 30 rows   PERMITTED  ✗
  INSERT public.agent_log         ->  1 row    PERMITTED  ✗

as authenticated, JWT sub = a legitimate non-Kerwin user

  SELECT public.user_bug_reports  ->  0 rows   cannot read them
  UPDATE public.user_bug_reports  -> 30 rows   ...but can overwrite all 30  ✗
  INSERT agent_log AS another uid ->  1 row    forged attribution accepted  ✗

The core fear was wrong — training data is safe. But two policies named "Service role updates bug reports" and "Service role inserts agent_log" are in fact TO public USING (true). service_role has rolbypassrls = true, so they do nothing for service_role; the only thing they do is grant the capability to anon and every signed-in user. Filed as BUG-78, migration 0005 written.

2 · There is no future "public share" moment. The URL is already public. The epic title says "before public URL share." tandem-fitness-tracker.netlify.app has been on the open internet the whole time. So BUG-74 did not harden ahead of exposure — it closed an exposure that already happened, for an unknown window, with real email addresses among the world-readable rows. Breach notification and a log review are both currently unscheduled.
3 · Under EPIC-30, the adversary stops being anon. A community library means open signup. The threat model becomes a signed-up authenticated user — free to become. Every policy written so far assumes authenticated is trustworthy. BUG-78's second probe is the proof: as a legitimate signed-in user, all 30 bug reports were writable.

The recommendation

  1. Rewrite EPIC-5 rather than close it. Keep the slot and the EPIC-30 gate; swap the contents. Demote P0 Critical → P1 High.
  2. New scope, in order: (1) write-side RLS audit · (2) auth_leaked_password_protection toggle · (3) signup-posture ruling · (4) pg_net out of public.
  3. Rotation is optional hygiene. Never a gate.
  4. Escalate the disclosure question to Kerwin. Not a technical decision.

Highest-leverage suggestion, from the Expansionist: productise the probe that found both bugs as scripts/rls-probe.mjs in npm run verify — every table × every role × read and write. Neither BUG-74 nor BUG-78 was caught by get_advisors, because RLS was on and policies existed; they were merely permissive. A data-access invariant gate, mirroring what scripts/doctrine.mjs does for exercise science.

The one thing to do first

Audit the write policies.

Everything else on this page is scheduling. That one was a live, unverified hole. Done — and it found two.
