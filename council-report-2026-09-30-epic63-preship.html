Verdict at the time of asking — do not merge

The branch contained a regression it had created itself. Two of its own fixes cancelled out, and all 36 green checks were structurally incapable of seeing it. cfgFromUserRow() returns a complete replacement config and did not build maxDb — which BUG-192 had just made the durable home for the dumbbell cap. syncFromCloud() runs on app boot for any signed-in user, so the cap was erased on essentially every load and dumbbell prescriptions went uncapped: the exact defect BUG-192 was filed to fix.

Verdict now — merge

Seam fixed and gated at the contract level (89ae5a2, SC-37). The five controls are now driven in a real browser and asserted on the DOM (38d41b3), which the council was four-to-one in calling the actual merge gate. verify 37/37, validate:personas green. Two DOM assertions were deleted along the way for failing to discriminate, and the investigation that exposed them produced a new filed finding.

Agreement

  • Browser verification was the gate, not the fix count — four of five, independently.
  • Per-bug gates were the structural weakness. N single-bug gates say "each fix still does its own job" and nothing about the seams between them.
  • The reads-side gate, not any fix, is the branch's most valuable artifact — Expansionist and First Principles, independently, for the same reason: it attacks the generator of the bug class.
  • BUG-191 (the button that displays a false confirmation) and BUG-199 (the injury promise the engine cannot keep) outrank the rest of the backlog — Contrarian and Outsider, independently.

The clash, and how it resolved

The Expansionist wanted an immediate merge on the premise that nothing here is worse than what is live. That premise was false when written — the seam regression made one fix actively worse than live. Once fixed, the disagreement reduced to cost, and the Executor priced the browser pass at one afternoon against a template that already existed. When the cheap option is also the one four advisors want, take it.

What the browser pass then found

The first DOM assertion written — "no rendered dumbbell load exceeds the cap" — passed, and passed again with the fix removed. It was vacuous: the fixture seeded a button tier name (hotel_small) where config takes the config vocabulary (home_dumbbells), so zero dumbbell exercises rendered and the filter matched an empty set. With the fixture corrected it still passed under mutation, because natural week-one seeds already sit under the cap. Forcing it to bind required a 200 lb working 1RM, which moves the render onto the calibrated branch — and dbCap is consumed only in seedWeight(), so it governs starting load alone. The assertion then failed on correct code.

Both assertions were deleted as non-evidence rather than left green. The investigation produced a genuine new finding, filed not fixed: an earned dumbbell 1RM is not clamped by the gym cap, so a traveller is prescribed weight the gym does not have. That needs an exercise-science ruling, not a blind clamp.
